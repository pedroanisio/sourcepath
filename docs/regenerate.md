# Regenerate

> User-facing overview (fidelity table, CLI invocation, what's lost, size
> cost): [README.md § Regenerate](../README.md#regenerate). This document
> is the extender's reference — read it when adding a new language to
> `_REGENERATORS`.

`codebase_mapper.regenerate` materializes source files from `inventory.ttl`
alone — specifically, from the `cbm:astSummary` JSON literal attached to each
`cbm:File` subject. No `blobs/` directory, no original repo, no network.

It is the lossy companion of `reconstruct` (which reads `inventory.ttl` +
`blobs/` for a byte-identical round-trip on every file). Currently supported
by `regenerate`: **Python** (semantic — re-parses to the same AST),
**TypeScript / JavaScript** (byte-identical via stored leaf-text CST).
Everything else is enumerated in the report and skipped.

## Pipeline plumbing

`regenerate` is one slice of a larger flow. The relevant pieces:

1. The pipeline calls a per-language `LanguageAnalyzer.extract(content, path)`
   which returns `(ast_summary: dict | None, errors: list[str])`.
   See [`codebase_mapper/inspection/pipeline.py`](../codebase_mapper/inspection/pipeline.py).
2. `ast_summary` is stored on the [`FileRecord`](../codebase_mapper/inspection/models.py)
   as a Python dict.
3. [`RdflibEmitter`](../codebase_mapper/emission/infrastructure/rdf/rdflib_emitter.py) JSON-encodes it
   (`json.dumps(..., sort_keys=True)`) and writes it as a plain string
   literal at `cbm:astSummary`:

   ```turtle
   cbmi:file/foo.py
       cbm:astSummary "{\"ast_json\": ..., \"language\": \"python\", ...}" .
   ```
4. [`regenerate`](../codebase_mapper/emission/application/regenerate.py) walks every `cbm:File`,
   reads `cbm:language` and `cbm:astSummary`, looks up the regenerator in
   `_REGENERATORS`, and writes the returned source under `out_dir/<path>`.

## Adding a new language

To add `regenerate` support for a language `L`:

### 1. Decide the fidelity model

You must choose one of:

- **Byte-identical** — the regenerated bytes equal the original bytes,
  `sha256(regen) == cbm:contentSha256`. Required if the file is meant to
  round-trip without churning the working tree.
- **Semantic** — the regenerated source re-parses to the same AST as the
  original. Comments, whitespace, quote style, and trailing punctuation may
  differ. Acceptable when downstream consumers only care about behavior.

Tree-sitter grammars have no built-in `unparse`, so byte-identical only
works if the extractor stores enough of the CST to walk back to source.
The TS/JS and Rust extractors do this; the remaining Go/Swift/Kotlin/etc.
extractors do **not** — they capture imports and symbol names but throw
the rest away.

### 2. Extend `ast_summary` so it carries enough to regenerate

This is the contract the regenerator depends on. There is no schema file —
the dict shape is whatever your extractor and your regenerator agree on.
But every implementation must:

- Always include `"language": "<your-lang>"`. This is for debugging; the
  actual dispatch uses `cbm:language`.
- Include a `"schema_version": <int>` so future extractor revisions are
  detectable. Bump it on every incompatible change. The regenerator should
  reject older versions explicitly (see Python: `raise ValueError("summary
  missing 'ast_json' (schema_version < 1 or serialize failed)")`).
- Be JSON-serializable by `json.dumps(..., sort_keys=True)`. Wrap any
  non-JSON values (bytes, complex, NaN, Ellipsis, tuples) in tagged
  dicts and invert them in the regenerator. See `_ast_to_jsonable` /
  `_jsonable_to_ast` in [`inspection/languages/python.py`](../codebase_mapper/inspection/languages/python.py)
  for the canonical pattern.
- Stay independent of source positions where possible. Storing line/column
  ranges blows up the literal size and is rarely needed for regenerate.

#### Pattern A: semantic regenerate (Python-style)

Store a JSON-encoded full AST. On regenerate, materialize the AST and call
the language's `unparse`. Example: [`extract_python_ast_summary`](../codebase_mapper/inspection/languages/python.py)
emits `{"ast_json": <serialized ast.Module>, ...}` and
[`regenerate_python_source`](../codebase_mapper/inspection/languages/python.py) calls
`ast.unparse` on it.

This is small and easy when the standard library (or a library like
`libcst`) provides an unparser. **It is lossy by definition** — comments and
formatting are gone.

#### Pattern B: byte-identical regenerate (TS/JS-style)

Store the full CST with every leaf's text plus interstitial gaps, plus any
bytes before the root node's `start_byte` (`header`) and after `end_byte`
(`footer`). On regenerate, walk the tree pre-order and concatenate every
string / `text` field. Example: `_ts_node_to_jsonable` →
`regenerate_tsjs_source` in [`inspection/languages/tsjs.py`](../codebase_mapper/inspection/languages/tsjs.py).

This is byte-perfect for valid UTF-8 input but expensive: in measured runs,
TS/JS `ast_summary` JSON is ~12.5× the source size. Track the cost via
`counts.ast_summary_total_bytes` in `run_manifest.json` and, if it matters,
add a sidecar (see "Size cost" in [README.md](../README.md)).

### 3. Implement the regenerator callable

Signature is fixed:

```python
def regenerate_<lang>_source(summary: dict) -> str: ...
```

Hard requirements:

- **Input**: the parsed `ast_summary` dict (already `json.loads`-ed).
- **Output**: the source text as a `str`. The driver writes it with
  `dst.write_text(source, encoding="utf-8")` — no trailing-newline handling
  on the driver side, so include it yourself if you want one.
- **Failure mode**: raise any exception with a useful message. The driver
  catches `Exception`, records `{"path": ..., "error": "<Type>: <msg>"}`
  in `report["regenerate_errors"]`, increments `by_language[lang].failed`,
  and continues — one bad file must never poison the run.
- **No I/O**: regenerators are pure functions of the summary dict. Don't
  read files, don't touch the network, don't import the original repo.
- **Determinism**: the same summary must produce the same bytes every time.
  Sort any iteration over dict keys.

### 4. Register the callable

In [`codebase_mapper/emission/application/regenerate.py`](../codebase_mapper/emission/application/regenerate.py), add
your callable to `_REGENERATORS`, keyed by the `cbm:language` literal that
your extractor produces (the same string stored in
`FileRecord.language`):

```python
from .languages.rust import regenerate_rust_source

_REGENERATORS: dict[str, Callable[[dict], str]] = {
    "python": regenerate_python_source,
    "typescript": regenerate_tsjs_source,
    "javascript": regenerate_tsjs_source,
    "rust": regenerate_rust_source,   # new
}
```

`supported_languages()` reads this dict, so no other change is needed for
the report's `supported_languages` field or for the per-language counts.

### 5. Add the contract test

Either extend [`tests/verify_regenerate.py`](../tests/verify_regenerate.py)
or ship a dedicated `tests/verify_<lang>_regenerate.py`. The shared file
is the original pattern (Python + TS/JS live there); the per-language
file is acceptable when the language's surface area or fixture set is
big enough to warrant isolation. Rust took the per-language path — see
[`tests/verify_rust_regenerate.py`](../tests/verify_rust_regenerate.py).

The test (wherever it lives) must include for the new language:

1. **Fixture**: at least one non-trivial source file covering the surface
   area you care about (imports, declarations, expressions, control flow,
   language-specific constructs).
2. **Per-language counts**: `report["by_language"][<lang>] ==
   {"ok": <n>, "failed": 0}` and the file appears in `files_regenerated`.
3. **Fidelity check**:
   - Byte-identical: `regen_bytes == orig_bytes` **and**
     `sha256(regen_bytes) == record.content_sha256`.
   - Semantic: parse both original and regenerated source with your
     language's parser and assert structural equality (the Python case
     uses `ast.dump(annotate_fields=True)` equality).
4. **Three mutations**, already covered generically but worth confirming
   your language doesn't break them:
   - Corrupt `cbm:astSummary` literal → file lands in `ast_parse_errors`,
     others still regenerate.
   - Missing `cbm:astSummary` triple → file lands in `no_ast_summary`.
   - `cbm:language` swapped to a foreign value → file lands in
     `ast_unsupported`.
5. **CLI parity**: `python -m codebase_mapper --regenerate --inventory I
   --out O --report R` exits 0 and the new files are present.

The test currently exits non-zero on any failure and is the canonical CI
gate for this feature.

### 6. Update size accounting (only if Pattern B)

If you store a full CST, also bump
[`emit_bundle.py`](../codebase_mapper/emission/application/emit_bundle.py) to count it. The
existing branch:

```python
elif (r.language in ("typescript", "javascript")
      and r.ast_summary.get("cst_json") is not None):
    ast_full_bodies_tsjs += 1
```

…should grow a counterpart for your language (e.g.
`ast_full_bodies_rust`). This keeps `run_manifest.json` honest about where
the inventory bytes go.

### 7. Update prose

Add a row in [README.md](../README.md) under "Regenerate" listing the new
language, its fidelity model, and the size ratio you measured. Note any
known losses (comments, formatting, encoding).

## Checklist

Before opening a PR:

- [ ] Extractor sets `language` and `schema_version` in the summary dict.
- [ ] Summary JSON-serializes via `json.dumps(..., sort_keys=True)` with
      no `TypeError`.
- [ ] Regenerator is a pure function: same summary → same bytes, no I/O.
- [ ] Regenerator raises (does not return empty/garbage) when the summary
      is missing required keys.
- [ ] Callable registered in `_REGENERATORS` under the exact
      `cbm:language` literal.
- [ ] `verify_regenerate.py` covers fixture + fidelity + three mutations +
      CLI parity for the new language and exits 0.
- [ ] If Pattern B: `emit_bundle.py` counts `ast_full_bodies_<lang>`.
- [ ] README updated with fidelity model and size ratio.


## Worked example: Rust (Stages 1-8)

Concrete reference implementation that anyone adding the next
tree-sitter language can copy from. Everything below is in-tree and
verified by the per-stage test suites.

### Summary shape

`codebase_mapper.languages.rust.extract_rust_ast_summary` returns:

```python
{
    "language": "rust",
    "schema_version": 1,                       # bump on incompatible changes
    "imports": [...],                          # cbm:imports source — flat list
    "mod_decls": [...],                        # top-level `mod foo;` declarations
    "top_level_functions": [...],              # legacy shape, kept for compat
    "top_level_classes": [...],                # legacy shape, kept for compat
    "items": [...],                            # Stage 1: rich symbol metadata
    "cst_json": <node | None>,                 # Stage 6: leaf-text CST
    "header": "<bytes before root.start_byte>",
    "footer": "<bytes after root.end_byte>",
}
```

`items` and `cst_json` are independent — Stage 1 made the parser-side
introspection rich; Stage 6 added the regenerate path on top.
Consumers that only need symbol metadata (xrefs, attribute queries)
read `items`; consumers that need to materialize bytes (regenerate)
read `cst_json` + `header` + `footer`.

### Schema versioning rule

`RUST_AST_SCHEMA_VERSION` (currently `1`) is defined as a module-level
constant in `languages/rust.py`. **Bump it whenever any of the
following changes incompatibly**:

- `cst_json` encoding (the `_ts_node_to_jsonable` output shape).
- `items[]` entry schema (kinds, parent semantics, range encoding).
- `header` / `footer` semantics.

The regenerator's first action is to assert `cst_json is not None`
and surface the version in the error message, so older bundles that
predate the bump get a clean `ValueError` rather than a wrong-bytes
roundtrip.

### CST capture pattern

`_ts_node_to_jsonable(node, content)` lives in `languages/rust.py`,
copied (not imported) from `languages/tsjs.py`. The function is
language-agnostic — it walks any tree-sitter `Node` — but each
language module owns a local copy so the dependency graph stays
strictly layered (no plugin imports a peer's private helper).

If a third tree-sitter language ever lands (e.g. Go regenerate),
extract `_ts_node_to_jsonable` to `ts_setup.py` as a public helper.
Two callers can each own a copy; three is the point where shared
ownership pays for itself.

### Header / footer

For Rust source files in our fixtures, `header` and `footer` are
almost always `""` — tree-sitter's `source_file` root spans the
entire input. The fields exist because:

- Shebang lines (`#!/usr/bin/env rust-script`) sit before the root.
- Trailing whitespace or end-of-file comments can sit after the root
  depending on the grammar version.

Discarding these silently would break byte-identical roundtrip on the
files that have them. Always capture, always emit.

### Verifier

The headline contract is in
[`tests/verify_rust_regenerate.py`](../tests/verify_rust_regenerate.py):
**`regenerate(extract(content)) == content`** asserted over every
Rust fixture in the repo, plus a synthetic file exercising irregular
whitespace, multi-line signatures, and absence of a trailing newline.

The counter contract (`ast_full_bodies_rust`) is in
[`tests/verify_rust_ast_body_count.py`](../tests/verify_rust_ast_body_count.py) —
a separate file because the surface area is wide enough (record-level
counting + source-grep regression net + MCP `bundle_summary` parity)
that interleaving it with the regenerate suite would obscure both.

### Measured size cost

For the existing Rust fixtures (~6 files totaling ~3 KB of source),
`ast_summary` JSON is roughly **10× source** — slightly less than
TS/JS (~12.5×) because the Rust grammar emits fewer anonymous
punctuation leaves per statement. Highly attribute-dense files push
the ratio higher; comment-dense files push it lower (comments are
captured as interstitial strings in `cst_json.children`, but they're
not tagged distinctly).

This number is **not** representative of large production codebases —
expect 8-15× depending on the dialect. Always measure with
`counts.ast_full_bodies_rust` + `counts.ast_summary_total_bytes`
before assuming the cost is acceptable for your scale.
