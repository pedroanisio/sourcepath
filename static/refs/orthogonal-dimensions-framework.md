# Orthogonal Dimensions for Software System Analysis

## 1. Purpose and scope

This framework classifies software systems along a fixed set of orthogonal, observable, descriptive dimensions, so that analysis, comparison, diagnosis, and design decisions can be made against a stable vocabulary instead of ad-hoc impressions. It is designed to be applied by humans and by AI agents, across languages, paradigms, domains, scales, and deployment models, and to survive technology fashion cycles. Its prose form is this document; its machine-readable form is the companion TBox and SHACL validation layer, and the two are kept in exact agreement.

The framework's admission rule, which the ontology calls the Scope-A rule, is strict: a concept belongs only if it describes an independently variable, observable, descriptive property of an intended or implemented software system. Concepts about stakeholders, viewpoints, rationale, architecture-description mechanics, governance, and external evaluation layers fall outside the scope unless they enter as evidence or as an explicitly quarantined overlay. Under that rule the framework defines twenty core system dimensions, grouped into six navigational categories, plus exactly one assessment overlay.

Five things are commonly confused with a dimension, and separating them is half the framework's value. An analysis region, such as "architecture" or "style," is a broad area of concern that bundles many properties: useful as a chapter heading, useless as a measurement instrument, and admitted here only as input. An orthogonal dimension is one clearly defined, observable property that varies independently and takes descriptive values; it is the unit of the framework. A quality attribute, such as latency or modifiability, is a desideratum with two legitimate forms: as a revealed priority it is descriptive and lives in the overlay, and as an achievement level it is evaluative and lives in the scoring layers — never as a raw dimension. A scoring rubric is a procedure mapping evidence to classification to assessment; it consumes dimensions but is not one. A subjective opinion is a judgment with no evidence procedure, excluded from classification entirely and admissible only in the recommendation layer, explicitly labeled as judgment.

## 2. What orthogonality means here

Strict mathematical orthogonality is unachievable for real systems. The framework claims something weaker but auditable. Definitional independence means no dimension is defined in terms of another dimension's value. Variational independence means that for every pair of dimensions, real systems exist at off-diagonal combinations: domain-decomposed monoliths and layer-decomposed microservice fleets both exist, and the framework must be able to say so without contradiction.

Two working rules make this operational. The first rule is that evidence is shared but properties are not. A single artifact — a Dockerfile, an import graph, a database schema — may serve as evidence for several dimensions, but each property of the system has exactly one home dimension. When an observation seems to belong to two dimensions, it is split into its constituent properties and each is filed in its home; section 6 does this for the common collisions. The second rule is that classification is descriptive while assessment is layered. Classification states what the system is, with evidence and confidence attached. Judgments of goodness, risk, maturity, and priority live in separate layers that consume classifications but never contaminate them.

Empirical correlation between dimensions is expected and is itself diagnostic signal: event-driven runtimes tend to have message contracts, and a system that breaks a common correlation deserves a question, not a re-classification.

## 3. How the set was derived

The framework began by testing five candidate regions — software architecture, component design, codebase organization, code quality, and programming style — against seven acceptance criteria: single property, independent variation, observability, non-subjectivity, non-technology-preference, usefulness, and universality. None survives as a dimension in its original form. "Architecture" is a scope of concern, not a property; under ISO/IEC/IEEE 42010 an architecture is a set of views addressing stakeholder concerns, and the standard itself refuses to treat it as one thing (ISO/IEC/IEEE 42010:2022 — verify independently). It dissolves into decomposition, dependency topology, connectors, contracts, state ownership, runtime execution, deployment, and trust boundaries. "Component design" differs from architecture by unit of analysis rather than by property, so scale becomes a parameter of the whole framework: every dimension applies fractally, at system, subsystem, or module scope, and every classification must state its scope. "Codebase organization" survives after narrowing to the purely physical layout of source, with its alignment to the logical decomposition demoted to a finding. "Code quality" splits three ways: quality as judgment is relocated to the scoring layers, quality attributes as revealed priorities become the assessment overlay, and observable quality ingredients such as duplication or complexity become evidence inside other dimensions. "Programming style" splits into the computational paradigm, the local idiom discipline, the type-and-data discipline, and the representation half of failure handling, with formatting aesthetics excluded as carrying near-zero diagnostic information in tool-normalized ecosystems.

Four boundary decisions then complete the set, and each is locked into the ontology by a dedicated SHACL shape so that no conforming instance of the framework can silently undo it. First, interaction mechanics are separated from both contracts and runtime execution into their own dimension: two units can share the same dependency edge and the same contract yet interact through direct calls, queues, streams, actor mailboxes, brokers, workflow engines, or tool invocations, and the delivery, ordering, synchrony, buffering, and failure semantics of that mediation are one coherent property with no other home (the connector concept follows the connector-as-first-class tradition — Mehta, Medvidović, and Phadke, "Towards a Taxonomy of Software Connectors," ICSE 2000 — verify). Second, variability and configuration space is admitted as a dimension. An earlier run of the admission test rejected a narrower candidate — runtime behavior varied through environment variables and flags — because its observations filed cleanly elsewhere; the residual property that does not file anywhere is the space of valid variants itself: variation points, variant constraints, binding times, and product-line structure (Pohl, Böckle, and van der Linden, *Software Product Line Engineering*, Springer, 2005 — verify). Runtime control surfaces remain evidence for observability, flag lifecycle remains evidence for evolution, and configuration-as-artifact remains evidence for build and delivery; the variant space is classified here. Third, programming paradigm and implementation idiom are split: a system can hold one computational model while its idiom discipline varies from exemplary to chaotic, and one idiom family can express several paradigms, so merging them forces a single value onto two independently varying properties. Fourth, testing is broadened into verification and assurance: correctness, safety, compatibility, and reliability claims are established both before release and during operation, so runtime monitors, canary validation, and production invariant checks belong with the pre-release portfolio rather than with observability, which keeps only the capacity to inspect and steer.

## 4. The canonical set

The framework contains twenty core dimensions and one overlay, in six categories. The categories are navigational, not load-bearing: orthogonality is claimed between dimensions, never between categories. The structural category holds decomposition (D01), dependency topology (D02), connector and interaction (D03), codebase physical organization (D08), and composition and reuse (D10). The boundary-and-information category holds interface and contract (D04), state and data ownership (D05), abstraction and encapsulation (D09), type and data discipline (D17), and security and trust boundaries (D19). The runtime-and-operational category holds runtime execution (D06), error handling and recovery (D16), and operational observability and control (D18). The lifecycle-and-evolution category holds deployment and distribution (D07), change and evolution (D11), variability and configuration space (D12), verification and assurance (D13), and build and delivery (D20). The code-expression category holds programming paradigm (D14) and implementation idiom and style (D15). The overlay category holds the quality-attribute prioritization profile (O01) alone. Every dimension applies fractally and every classification states its scope.

### D01. Decomposition model

Asks by what criterion, and at what granularity, the system is partitioned into conceptual units. Its unit of analysis ranges over system, subsystem, service, package, module, bounded context, and repository. It measures the boundary criterion, unit granularity, responsibility allocation, and the dominant partitioning logic; it does not measure dependency direction, interaction mechanism, deployment placement, or physical file layout. It is orthogonal because the same decomposition can carry different dependency rules, connector mechanisms, source layouts, and deployment forms. Evidence comes from source code, repository structure, package or module layout, and architecture diagrams; example values are partitioning by layer, by feature, and by bounded context. Diagnostically it reveals change blast radius, conceptual coherence, boundary ambiguity, and modularization risk; its characteristic failures are mixed decomposition criteria, god modules, unclear ownership, and cross-cutting feature leakage.

### D02. Dependency topology

Asks what shape, direction, and allowed structure the dependency relations among units take. Its unit of analysis is a graph: module, package, service, build, or library. It measures graph direction, layering rules, cycles, fan-in and fan-out topology, and permitted dependency paths; it does not measure connector semantics, the shape of interface contracts, or coupling strength as a metric — coupling intensity is evidence, not a dimension. It is orthogonal because graph shape varies independently of unit decomposition, contracts, runtime model, and physical organization. Evidence comes from generated dependency graphs, build files, source code, and package layout; example values are strictly layered dependencies, a directed acyclic graph, and cyclic dependencies. Diagnostically it reveals cycle risk, architectural erosion, ripple paths, and hidden central hubs; its failures are dependency cycles, forbidden layer crossings, unstable dependency direction, and accidental hubs.

### D03. Connector and interaction model

Asks how interaction between units is mediated, coordinated, synchronized, ordered, buffered, delivered, and failed. Its unit of analysis is the connector itself: an edge, call path, message path, workflow link, tool invocation, or event channel. It measures the interaction mechanism, coordination semantics, delivery and ordering guarantees, synchrony, backpressure, and failure behavior; it does not measure merely who depends on whom, nor the static contract exposed at a boundary. It is orthogonal because two units can hold the same dependency and the same contract yet interact through direct calls, queues, streams, actor mailboxes, brokers, workflow engines, or tool calls; and the mediation between units is distinct from the intra-unit runtime execution model, since the same connector can operate under different execution models and the same execution model can drive different connectors. Evidence comes from source code, API schemas, runtime topology, deployment manifests, and runtime logs; example values are direct-call, message-queue, publish-subscribe, stream, and actor-mailbox connectors. Diagnostically it reveals coordination risk, temporal coupling, retry storms, message loss, implicit integration, and connector mismatch; its failures are the database used as a connector, unbounded queues, hidden synchronous calls, unclear delivery semantics, and mismatched interaction assumptions.

### D04. Interface and contract model

Asks how boundaries expose capabilities and how the semantics, schemas, compatibility, and error contracts of those boundaries are specified and enforced. Its unit of analysis is a boundary: an API, module or class interface, CLI, event schema, protocol boundary, or tool contract. It measures contract explicitness, schema discipline, versioning, compatibility policy, and boundary semantics; it does not measure the runtime mechanics of the connector carrying the contract, nor the state authority behind the boundary. It is orthogonal because the same contract can travel over different connectors and the same connector can carry different contract styles. Evidence comes from API schemas, contract tests, source code, and operational runbooks; example values are schema-first, code-first, and implicit contracts. Diagnostically it reveals contract drift, implicit semantics, breaking-change risk, and integration fragility; its failures are implicit contracts, shared-database contracts, undocumented error semantics, and version drift.

### D05. State and data ownership model

Asks where authoritative state lives, which unit may mutate which data, and how state authority is partitioned. Its unit of analysis is a body of state: a data store, aggregate, service, bounded context, cache, event store, or global state object. It measures source-of-truth allocation, write authority, state lifetime, shared mutable state, synchronization, and ownership granularity; it does not measure schema shape alone, type discipline, or API style. It is orthogonal because the same schema can live under different ownership regimes, and the same decomposition can share or separate state authority. Evidence comes from database schemas, migration scripts, source code, and runtime topology; example values are shared-database ownership, single-writer ownership, and event-sourced ownership. Diagnostically it reveals split-brain risk, integration-by-database, ownership ambiguity, cache incoherence, and transaction-boundary risk; its failures are multiple writers without an authority model, global mutable state, ambiguous sources of truth, and shared-database coupling.

### D06. Runtime execution model

Asks how the system executes at runtime, covering concurrency, scheduling, control flow, and execution coordination. Its unit of analysis is an execution context: process, thread, event loop, actor, worker, job, agent loop, or batch process. It measures the concurrency model, scheduling style, execution lifecycle, blocking behavior, control-flow regime, and work dispatch; it does not measure where artifacts are deployed or how source is organized. It is orthogonal because the same deployment can host different execution models and the same paradigm can run under different execution styles; intra-unit execution semantics are distinct from the connector and interaction model that mediates between units. Evidence comes from source code, runtime topology, runtime logs, and deployment manifests; example values are single-threaded, thread-per-request, event-loop, actor, batch, and agentic-loop runtimes. Diagnostically it reveals deadlock, event-loop blocking, priority inversion, uncontrolled concurrency, and throughput bottlenecks; its failures are blocked event loops, unbounded threads or goroutines, hidden scheduler coupling, and unsafe shared concurrency.

### D07. Deployment and distribution model

Asks how built artifacts are placed, installed, published, or arranged across runtime or consumer environments. Its unit of analysis is the placement target: a runtime node, container, function, package registry, mobile app, embedded firmware, edge node, or client installation. It measures artifact placement, runtime distribution, hosting topology, install model, package publishing, and availability surface; it does not measure how source becomes an artifact, nor what execution semantics the artifact uses once running. It is orthogonal because build pipeline, runtime execution, and deployment topology vary independently — the same event-loop binary behaves identically on a laptop and in an orchestrated fleet. Evidence comes from deployment manifests, runtime topology, build files, and CI/CD configuration; example values are single-node deployment, container-orchestrated deployment, serverless deployment, and package-registry distribution. Diagnostically it reveals operational blast radius, environment coupling, rollout complexity, and placement risk; its failures are environment-specific behavior, undeclared placement assumptions, package or install drift, and weak rollout strategy.

### D08. Codebase physical organization

Asks how source artifacts are physically arranged across repositories, directories, packages, modules, and files. Its unit of analysis is the storage structure itself: repository, workspace, package, directory, module, file. It measures repository topology, package layout, directory conventions, naming and location rules, and artifact grouping; it does not measure the logical decomposition or the runtime deployment — alignment between physical layout and logical decomposition is a finding, not part of either classification. It is orthogonal because one logical decomposition can be represented by many physical layouts and one layout can hide different logical architectures; a pure file-move refactor changes this dimension while touching no other. Evidence comes from repository structure, package or module layout, source code, and build files; example values are monorepo organization, polyrepo organization, and package-by-feature layout. Diagnostically it reveals navigation cost, discoverability, accidental coupling through location, and atomic-change friction; its failures are architecture hidden by folder layout, package-by-layer confusion, scattered ownership, and generated code mixed with hand-written source.

### D09. Abstraction and encapsulation model

Asks how implementation details, invariants, and internal representations are hidden behind stable abstractions. Its unit of analysis is a hiding boundary: module, class, component, API, aggregate, package, or library edge. It measures information hiding, invariant protection, visibility discipline, boundary enforcement, and representation exposure; it does not measure how units are composed or reused, nor the shape of the dependency graph. It is orthogonal because units can compose the same way while exposing very different amounts of internal knowledge. Evidence comes from source code, API schemas, package layout, and static-analysis configuration; example values are opaque-module encapsulation and concretion-exposed encapsulation — deliberate data transparency is a legitimate value, not a failure. Diagnostically it reveals abstraction leakage, representation exposure, invariant bypass, and brittle internals; its failures are primitive obsession at boundaries, public mutable internals, abstractions that hide nothing, and bypassed aggregate rules.

### D10. Composition and reuse model

Asks how units are combined, reused, extended, generated, configured, or assembled into larger capabilities. Its unit of analysis is an assembly point: component, library, plugin, module, function, template, generated artifact, or reusable capability. It measures the reuse strategy, extension mechanism, composition mechanism, plugin model, inheritance versus delegation, code generation, and library-extraction posture; it does not measure what is hidden behind abstractions or how dependencies are directed — composition is the mechanism, topology is the result. It is orthogonal because the same encapsulation style can be combined through inheritance, delegation, plugins, configuration, generated code, or pipelines. Evidence comes from source code, repository structure, build files, and API schemas; example values are plugin composition, library composition, and generated-code composition. Diagnostically it reveals reuse friction, accidental framework lock-in, inheritance fragility, and extension-point ambiguity; its failures are copy-paste reuse, inheritance abuse, plugin contract drift, and over-abstracted shared libraries.

### D11. Change and evolution model

Asks how the system absorbs change over time through compatibility, migration, deprecation, and extension mechanisms. Its unit of analysis is a change class across a stated horizon: an API, data schema, release, module, feature, extension point, or migration path. It measures compatibility policy, deprecation lifecycle, migration strategy, feature evolution, backward compatibility, and upgrade path; it does not measure simultaneous configurable variants, which belong to D12. It is orthogonal because a system can be highly configurable yet poor at evolution, or stable over time with little variability, and rigid-compatibility systems ship daily while promise-free systems ship yearly. Evidence comes from migration scripts, API schemas, CI/CD configuration, and source code; example values are semantic-version evolution and expand-contract migration. Diagnostically it reveals breaking-change risk, migration debt, compatibility lock-in, and extension-point decay; its failures are eternal feature flags, missing expand-contract migrations, unversioned contracts, and breaking-change cascades.

### D12. Variability and configuration-space model

Asks how the valid variants of the system are represented, constrained, selected, bound, and combined across build time, deployment time, tenant time, runtime, and user time. Its unit of analysis is the variant space: a feature, variation point, variant, product line, tenant profile, plugin set, build profile, or runtime capability profile. It measures variation points, variant constraints, binding time, the feature model, configuration validity, and the resulting product or configuration space; it does not measure temporal evolution, migration, or compatibility policy — those are D11. It is orthogonal because the selectable configuration space varies independently of decomposition, deployment, runtime, and temporal evolution. Evidence comes from feature-flag configuration, product configuration, build files, source code, and test suites; example values are feature-flag variability, product-line variability, and tenant-specific variability. Diagnostically it reveals invalid-configuration risk, feature interaction, test-matrix explosion, tenant drift, and hidden product-line complexity; its failures are unbounded feature combinations, undocumented variation points, configuration spaghetti, impossible test matrices, and tenant-specific forks.

### D13. Verification and assurance model

Asks how correctness, safety, compatibility, and reliability claims are established, both before release and during operation. Its unit of analysis is the assurance portfolio: test suites, verification targets, contracts, invariants, monitors, canaries, SLOs, and safety cases. It measures the testing portfolio, static analysis, formal methods, contract tests, runtime monitors, canary validation, chaos testing, and the assurance evidence they produce; it does not measure the achieved quality level, nor the release-pipeline mechanics that run the gates. It is orthogonal because verification strategy varies independently of architectural style, deployment model, paradigm, and runtime execution. Evidence comes from test suites, contract tests, static-analysis configuration, telemetry configuration, and CI/CD configuration; example values are a unit-integration-e2e portfolio, formal-verification assurance, and runtime-invariant assurance. Diagnostically it reveals unverified contracts, brittle tests, missing runtime assurance, weak oracles, and insufficient evidence for high-risk behavior; its failures are over-reliance on end-to-end tests, absent contract tests, non-deterministic tests, missing production invariant checks, and missing safety evidence.

### D14. Programming paradigm model

Asks what dominant computational model the code uses to express behavior. Its unit of analysis ranges over module, package, service, subsystem, and codebase, since real codebases are rarely uniform. It measures the paradigm posture — object-oriented, functional, procedural, declarative, logic, dataflow, actor-based, reactive, or agentic loop-based expression; it does not measure whether the code follows local language idioms or formatting conventions, which is D15. It is orthogonal because a system can hold one paradigm under many idioms, and one idiom family can express several paradigms; language does not determine it. Evidence comes from source code, static-analysis configuration, and package layout; example values are the object-oriented, functional, procedural, declarative, and agentic-loop paradigms. Diagnostically it reveals paradigm mismatch, inconsistent computational models, state and control-flow mismatch, and maintainability risk from mixed paradigms; its failures are accidental paradigm mixing, an object-oriented shell around procedural scripts, a functional facade hiding mutation, and declarative configuration with imperative side effects.

### D15. Implementation idiom and style model

Asks what local language, framework, community, naming, formatting, and metaprogramming conventions the implementation follows, and how coherently. Its unit of analysis ranges from file through module and package to codebase and framework integration point. It measures idiom coherence, naming and formatting discipline, framework-idiom alignment, metaprogramming posture, and local expression consistency; it does not measure the computational paradigm itself, nor objective quality by itself. It is orthogonal because the same paradigm can be idiomatic or unidiomatic within a given ecosystem, and style can vary without any change to architecture. Evidence comes from source code, static-analysis configuration, and repository structure; example values are idiomatic and unidiomatic implementation, judged against observable ecosystem norms rather than taste. Diagnostically it reveals readability friction, onboarding cost, idiom mismatch, style fragmentation, and framework misuse; its failures are mixed naming schemes, unidiomatic framework use, excessive magic, reflective behavior without convention, and quality claims resting on style alone.

### D16. Error-handling and recovery model

Asks how failures are represented, propagated, contained, recovered from, compensated, and escalated. Its unit of analysis is a failure path spanning function, module, service, process, workflow, job, and runtime boundary. It measures failure representation, propagation discipline, containment boundaries, retry and compensation strategy, supervision, dead-letter handling, and escalation; it does not measure general observability or verification strategy, though both may supply evidence. It is orthogonal because failure handling varies independently of runtime execution model, connector model, and interface style. Evidence comes from source code, API schemas, runtime logs, operational runbooks, and CI/CD configuration; example values are the exception model, the result-or-either model, and the supervisor recovery model. Diagnostically it reveals swallowed errors, retry storms, partial-failure incoherence, missing compensation, and weak containment; its failures are catch-all suppression, exception tunneling, retries without idempotency, missing dead-letter paths, and inconsistent error contracts.

### D17. Type and data discipline

Asks how types, schemas, validation, and data modeling constrain states, encode invariants, and prevent invalid data movement. Its unit of analysis is a data definition or trust-boundary crossing: type, schema, DTO, value object, database constraint, validation boundary, or serialization model. It measures static-versus-dynamic type posture, schema enforcement, validation placement, domain modeling, invariant encoding, and data-shape discipline; it does not measure programming paradigm or state-ownership authority. It is orthogonal because dynamic systems can enforce strict runtime schemas while statically typed systems can remain stringly typed and weakly modeled. Evidence comes from source code, API schemas, database schemas, and static-analysis configuration; example values are static type discipline, runtime schema discipline, and stringly typed discipline. Diagnostically it reveals validation gaps, primitive obsession, representable illegal states, schema drift, and boundary trust mistakes; its failures are stringly typed domains, scattered validation, unbounded any-or-object usage, missing database constraints, and unchecked deserialization.

### D18. Operational observability and control model

Asks whether the running system can be inspected, understood, and safely steered without redeploying. Its unit of analysis is a running unit: process, service, job, tenant, deployment, feature flag, health endpoint, or dashboard. It measures the telemetry model, correlation discipline, health and readiness semantics, feature flags, administrative controls, kill switches, configuration reload, and intervention paths; it does not measure the verification portfolio or the deployment placement by itself. It is orthogonal because a system can be deployable but unobservable, observable but hard to control, or strongly controlled under many runtime and deployment models. Evidence comes from telemetry configuration, runtime logs, operational runbooks, deployment manifests, and source code; example values are logs-metrics-traces observability and feature-flag control. Diagnostically it reveals blind spots, noisy alerts, missing intervention levers, weak incident triage, and unsafe runtime control; its failures are missing trace correlation, ambiguous health checks, absent kill switches, dashboard-only observability, and alert floods.

### D19. Security and trust-boundary model

Asks where trust changes level and how identity, authorization, authority, isolation, secrets, policy, and protected data are structured across those transitions. Its unit of analysis is a boundary where authority changes: trust, tenant, identity, policy, service, data, or secret boundary. It measures trust-boundary placement, the identity model, the authorization model, tenant isolation, secret handling, policy enforcement, and authority flow; it does not measure network or deployment topology by itself, nor general code quality — network position is a claim about trust, never a classification of it. It is orthogonal because trust layout can differ from network layout: segmented deployments can carry weak trust models while flat deployments enforce zero trust per call. Evidence comes from security policies, access-control configuration, source code, deployment manifests, and API schemas; example values are the perimeter model, the zero-trust model, and the tenant-isolation model. Diagnostically it reveals ambient authority, confused-deputy risk, trust by network position, tenant-breakout risk, and authorization gaps; its failures are perimeter-only authentication, missing object-level authorization, secret sprawl, shared tenant state, and implicit service trust. For agent systems this dimension asks whether the tool boundary is an enforced authorization perimeter, since untrusted text reaching state-changing tools is the injection surface (Greshake et al., 2023 — verify).

### D20. Build and delivery model

Asks how source becomes versioned, tested, packaged, signed, promoted, and released artifacts. Its unit of analysis is the path from commit to release: build graph, artifact, pipeline, release channel, package, image, binary, or generated artifact. It measures build reproducibility, artifact strategy, release cadence, promotion path, gating, signing, packaging, and delivery workflow; it does not measure where the artifact is deployed or installed after release. It is orthogonal because the same deployment model can be fed by different pipelines and the same build process can produce artifacts for different deployment forms. Evidence comes from build files, CI/CD configuration, static-analysis configuration, and repository structure; example values are the hermetic build model, the manual release model, and the trunk-based delivery model. Diagnostically it reveals non-reproducibility, supply-chain risk, manual release fragility, environment drift, and weak gating; its failures are unpinned builds, manual packaging, absent artifact provenance, snowflake pipelines, and generated files outside control.

## 5. The assessment overlay

### O01. Quality attribute prioritization profile

The single overlay records which quality attributes the system appears to prioritize when trade-offs occur: the revealed ordering among qualities such as performance, availability, consistency, security, evolvability, operability, cost, simplicity, and usability. It is descriptive — synchronous replication says consistency outranks latency, aggressive caching says the reverse — and it does not measure a generic quality score or any independent structural property. Its diagnostic value is the mismatch between stated priorities and actual structural decisions, the systematized form of the sensitivity and trade-off points in ATAM (Kazman, Klein, and Clements, SEI CMU/SEI-2000-TR-004, 2000 — verify). The overlay is deliberately second-order: it is read across the twenty core dimensions rather than off disjoint artifacts, which is why it is quarantined in its own category and must never be treated as an orthogonal peer dimension — a rule the ontology enforces with a dedicated shape. It is retained despite the impurity because revealed priorities are genuinely observable, the stated-versus-revealed gap is among the highest-value findings an audit produces, and excluding it reliably causes evaluators to smuggle priorities into the descriptive dimensions.

## 6. Keeping the dimensions apart

The pairs that cause most misclassification each have a discriminating test. Decomposition against physical organization: a pure file-move refactor changes D08 and cannot change D01; their alignment is a finding, never a shared classification. Topology against coupling: topology is the shape of the reference graph, coupling is an intensity measurement on edges that files as evidence — import fan-in strength to D02, wide chatty contracts to D04, shared mutable state to D05 — and saying "high coupling" without a home dimension is a rubric violation. Topology against connectors: D02 counts only compile-, link-, or import-time knowledge, while runtime interaction edges through queues or HTTP are D03 facts. Connectors against contracts: the mediation mechanics — delivery, ordering, synchrony, backpressure — are D03, while the boundary's specified semantics, schema, and compatibility policy are D04; the same schema-registered event contract can ride a queue or a stream. Connectors against runtime: the mediation between units is D03 and the execution semantics within a unit are D06 — the same connector can be driven by different execution models, and the reverse. Contracts against ownership: a database schema shared by two writers is a contract fact filed under D04 and a write-authority problem filed under D05. Abstraction against composition: what is hidden is D09, the mechanism by which parts combine is D10. Runtime against deployment: moving the same binary from a laptop to an orchestrated fleet changes D07 and leaves D06 identical, while rewriting thread-per-request to asynchronous on unchanged infrastructure does the reverse. Evolution against variability: change absorbed over time is D11, variants coexisting at one moment are D12 — a flag's lifecycle is D11 evidence, the variant space the flags define is D12. Assurance against observability and against delivery: how claims are established is D13, the capacity to inspect and steer is D18, and the pipeline that runs the gates is D20 — a gate's existence is D20 structure, its verification content is D13. Paradigm against idiom: the computational model is D14, the local dialect discipline is D15, and "consistently procedural" plus "unidiomatic for the ecosystem" is two classifications, not one. Trust against deployment: a flat network can carry per-call zero trust, so network diagrams are D07 evidence and, at most, claims about D19 to be verified against enforcement code. Discipline against paradigm: where invariants are encoded is D17 regardless of whether the code is object-oriented or functional. The overlay against everything: mechanisms are means and file under D01 through D20; the revealed priority ordering they imply is the O01 reading; never file a mechanism under the overlay or a priority under a mechanism.

When an observation still resists filing, decompose it into atomic properties and file each in the dimension whose discriminating question it answers. If two dimensions still claim the same atomic property, the framework has a defect: log it against the extension rules of section 10 rather than double-filing. Cross-dimensional implications, such as weak data discipline exactly at a trust boundary, are recorded as findings in the scoring layers, never as classifications.

## 7. Classification rubric

Classification begins by inventorying evidence sources ranked by evidentiary strength, from enforced artifacts such as compiler visibility, CI gates, architecture tests, IAM policies, and database constraints, through executable artifacts such as code, tests, configurations, manifests, and migrations, then structural artifacts such as repository layout, dependency graphs, and schemas, then declarative documents such as ADRs, docs, and diagrams — which are claims to verify — and finally testimony. Classification proceeds per dimension and per scope, stated explicitly; heterogeneous systems receive per-region values plus a named dominant value, never a forced single value. Two ledgers are kept: an observation ledger of artifact-anchored facts with paths, and an inference ledger of conclusions with their reasoning; a classification cites observations, and its confidence reflects the inference distance. Contrary evidence is recorded alongside supporting evidence, since a classification with no acknowledged counter-signals in a large system is suspect. Unknown is a first-class value: an unknown with a note about what evidence would settle it beats a guess in every downstream use.

Confidence takes exactly four values, matching the ontology's application shape. High means directly observable from enforced or executable artifacts examined directly — declarative documents alone can never yield it. Medium means strongly inferred from at least two independent executable or structural sources, or from enforced artifacts sampled rather than exhaustively examined. Low means plausible but weakly evidenced: a single source, documents or testimony only, or significant unresolved counter-evidence. Unknown means insufficient evidence, recorded together with what would settle it. Documentation describes the intended system and code is the actual system; when they diverge, the actual is classified and the intended-versus-actual delta is recorded as a finding, often the most valuable output of the audit.

## 8. Scoring layers

Assessment is layered above classification, and aggregation across dimensions happens only in the last two layers, with explicit weights, never overwriting the layers below. No single quality score is produced, because collapsing twenty orthogonal facts into one scalar destroys exactly the information the framework exists to preserve; if a stakeholder demands one number, it is computed in the final layer with published weights and labeled as a weighted opinion.

The first layer is descriptive classification: value, evidence, and confidence per dimension per scope, reusable across audits and audiences. The second is diagnostic assessment, producing findings from three coherence checks — internal, asking whether a dimension's value is consistently held or contested across regions; cross-dimensional, asking whether the combination carries known hazards, such as shared-store multi-writer ownership under independently deployed units, or implicit contracts meeting trusting data discipline exactly at a trust boundary; and contextual, asking whether the profile fits the system's stated requirements and the overlay's revealed priorities. Cross-dimensional findings are where the framework pays for itself, since they are visible only because the dimensions were kept apart. The third layer is maturity per dimension, measuring the intentionality and enforcement of the practice rather than the sophistication of the value chosen: accidental, conventional, explicit, enforced, and verified, never averaged across dimensions — a deliberate, documented, enforced shared-database design can outrank an accidental microservice split. The fourth layer is risk, always scenario-conditioned: a finding becomes a risk only relative to a change class, a load event, an attack, or a departure, scored as likelihood and impact with the blast radius read from the decomposition, topology, ownership, and deployment classifications, following the SEI quality-attribute-scenario shape (Bass, Clements, and Kazman, *Software Architecture in Practice*, 4th ed., 2021 — verify). The fifth layer ranks recommendations by risk, improvement leverage, cost, and confidence, with weights stated; leverage rewards single interventions that discharge multiple findings, and low-confidence findings route to evidence-gathering actions rather than remediation.

## 9. Two worked vignettes

A ten-year-old business-to-business monolith classifies, at system scope, as layered decomposition with two emergent domain packages (D01), convention-only layering with cycles through shared utilities (D02), in-process direct-call connectors plus one worker queue (D03), code-first external contracts with implicit internal ones (D04), a centralized single-writer store mediated by one ORM (D05), thread-per-request execution with cron batches (D06), a single deployable replicated behind a load balancer (D07), a type-grouped monorepo (D08), concretion-exposed encapsulation with ORM entities crossing every layer (D09), inheritance-and-mixin composition (D10), disciplined expand-contract migrations with no internal compatibility policy (D11), a small tenant-and-flag variant space bound at runtime (D12), a unit-heavy gating portfolio with no runtime invariant checks (D13), object-oriented paradigm (D14), strongly framework-idiomatic style (D15), exception representation with a global handler and queue-only retries (D16), dynamic typing with validation concentrated at the form layer (D17), request logs and metrics with restart as the only control (D18), perimeter authentication with tenancy by query convention (D19), and a locked, weekly release train (D20). The overlay reads delivery cadence above modifiability above latency, implied by SLOs only. The highest-value findings are cross-dimensional: exposed ORM entities (D09) against centralized state (D05) make schema changes the dominant change cost, and tenancy by convention (D19) with a trusting interior (D17) is one forgotten query scope from a data leak.

An internal support-automation agent classifies as capability-partitioned decomposition across loop, tools, memory, and policy (D01), an inverted core with tools and the model client behind interfaces (D02), a connector mix of direct calls and bounded asynchronous tool fan-out (D03), versioned JSON-schema tool contracts with an inherently implicit prompt-to-model contract (D04), single-writer session state beside a vector memory with no clear eviction owner (D05), a step-budgeted agentic loop (D06), a hybrid placement of orchestrator, external vendor endpoint, and tool sidecars (D07), a domain-grouped monorepo (D08), an interface-first tool boundary with prompt templates concretion-exposed (D09), plugin-registry tools with configuration-assembled prompts (D10), pinned model and prompt versions with eval-gated upgrades and vendor-forced change as its own class (D11), per-tenant capability profiles as a small explicit variant space (D12), an eval-suite statistical oracle plus tool unit tests, an injection red-team set, and runtime budget monitors (D13), declarative prompts and schemas orchestrated by imperative loop code (D14), idiomatic within each dialect with a clean seam (D15), a tool-failure taxonomy with idempotency keys and human escalation (D16), model outputs schema-validated before dispatch (D17), full prompt and tool-call tracing with a kill switch (D18), the tool boundary engineered as the authorization perimeter while untrusted text still enters planning (D19), and standard CI with the eval gate wired in (D20). The overlay reads safety and containment above task success above cost above latency. ## 10. Extending the set

A proposed dimension is admitted only if all seven conditions pass, and the test is recorded as a miniature decision record so the framework's own evolution follows the discipline of D11. The candidate must name a property with no existing home, shown by attempting to file three of its typical observations into the current dimensions and failing. It must vary independently, demonstrated with real systems that differ on the candidate while matching on all twenty, and conversely for at least three existing dimensions. It must specify enforced, executable, or structural artifacts that would classify it, rejecting any candidate whose best evidence is testimony. It must be technology-neutral, statable without naming a product or vendor, since anything that cannot be so stated is a value of an existing dimension. It must yield diagnosis, naming at least two failure modes only it reveals and a decision it would change. It must not be a rename, meaning its discriminating question must not paraphrase an existing one. And it must not be a preference: two competent evaluators given the same artifacts must converge.

Candidates are rejected immediately if their name contains a value judgment, names a technology, cannot be unknown, can only be assessed relative to taste, classifies the team rather than the system, or aggregates other dimensions. Rejected candidates are converted rather than discarded: extract the observable kernel, route each atomic property to its home dimension as a value or as evidence, push residual judgment into the scoring layers, and only run the admission test if a genuinely homeless property remains. The history of D12 illustrates both outcomes of the test. The narrow candidate "configuration model," meaning runtime behavior varied through environment and flags, fails: control surfaces file under D18, configuration-as-delivery-artifact under D20, flag lifecycle under D11, and configuration schema validation under D17. The residual property that files nowhere — the space of valid variants, with its variation points, constraints, and binding times — passes all seven conditions and is D12. Running the test honestly on the routed remainder is exactly how the set grows without decaying into a region list.

Common classification mistakes deserve standing warnings. Normative creep lets "should" contaminate "is," and the instant tell is an adjective inside a classification value. Technology-name substitution treats products as classifications, when products are evidence for values and never values. Intended-versus-actual conflation classifies the diagram instead of the code; the actual is classified and the delta reported. Halo and horn effects let one impressive or awful dimension drag its neighbors, which is precisely what scoring dimensions apart prevents. Single-value forcing flattens heterogeneous systems; classification is per region with a named dominant. Confidence inflation marks inference as observation, and documents alone never yield high confidence. Correlation-as-identity copies priors into classifications, when correlations are priors to check. Aggregate laundering produces a single architecture score, which lives only in the final layer, weighted and labeled as opinion. Humans use the framework for due diligence, decision-record framing, onboarding maps, and incident retrospectives; AI agents use the twenty questions as a structured probe plan over a repository, anchor every classification to artifact paths, never fill an unknown, treat documentation as claims to verify against code, and cap confidence mechanically by the rubric, so that human and agent audit outputs remain mergeable and diffable.
